# HackMate 产品信息补全草案

> 状态：草稿，待人工编辑确认  
> 用途：登记本次产品评审中发现的信息缺口、规则缺口和建议补充项，作为后续完善 `docs/idea.md` 和进入开发前的检查清单。

## 1. 文档目的

当前需求已经定义了 HackMate 的主要功能和用户主流程，但仍有一些会影响用户完成现场组队的信息和规则尚未明确。

本文重点补充三类内容：

1. 用户在不同页面需要看到、帮助其做出判断的信息。
2. 产品在申请、审核、组队完成等环节需要明确的状态和规则。
3. 本阶段实现时可采用的建议默认值，供人工决策。

## 2. 当前产品定义摘要

HackMate 是一个黑客松现场组队网页应用，当前已明确的功能包括：

- 手机号 + 6 位数字验证码登录；开发阶段不真实发送验证码，生成后直接显示在页面输入框下方。
- 广场展示当前组队公告，支持查看队伍详情。
- 队伍详情展示项目简介、队长、名额、当前人数、队员要求和组队状态。
- 用户可以申请加入队伍，提交文字介绍；PDF、图片、视频上传本阶段不实现。
- 申请后等待队长审核，通过后用户出现在队伍成员列表中。
- 用户可以创建队伍，创建后成为队长。
- 首页提供“我的队伍”入口；队长可以查看申请、同意或拒绝，拒绝理由选填。
- 支持退出登录，以便切换其他账号继续操作。

本阶段实现边界：

- 文件、图片、视频上传功能不实现。
- 除附件上传外的其他已描述功能均需实现。

## 3. 总体结论

当前方案已经覆盖“浏览队伍 → 申请加入 → 队长审核 → 加入队伍 / 创建队伍 → 我的队伍”的主流程。

但从使用者角度看，仍然缺少足够的信息来帮助用户判断、决策和完成后续动作。主要缺口集中在：

- 申请人没有可被队长判断的身份和技能画像。
- 队伍详情缺少招募角色、名额口径、现场位置等关键信息。
- 组队状态、满员规则、成员数量规则没有定义。
- 申请提交后缺少状态反馈和通知闭环。
- 队长审核缺少名额冲突、拒绝理由可见性等操作规则。
- 审核通过后缺少联系方式，无法真正完成现场组队。
- 队伍创建后的编辑、退出、移除成员、解散等生命周期操作未定义。
- 缺少当前活动、截止时间、地点等现场上下文。
- 登录账号规则、验证码生命周期和退出后的状态处理不完整。
- 移动端适配、空状态、错误状态和重复提交等体验细节未定义。

建议优先补齐 P0 项；P1 项可以在不阻塞主流程的前提下逐步完善。

## 4. 关键缺口与建议

### P0-1：用户身份画像与申请资料不足

**当前情况**

用户以手机号和验证码登录，申请加入队伍时提交一段文字介绍。除此之外，没有定义用户资料，也没有定义队长审核时能看到哪些信息。

**用户影响**

- 队长无法判断申请人是否具备所需技能、适合什么角色。
- 申请人不知道应该填写哪些内容，容易只写一句“想加入”，导致审核信息不足。
- 通过后成员之间缺少必要的身份辨识信息。
- 手机号等敏感信息如果直接展示，存在隐私问题。

**建议补充**

用户资料至少包含：

- 显示名称 / 昵称。
- 学校或公司。
- 技能标签。
- 希望担任的角色。
- 个人简介或项目经历。
- 联系方式，例如手机号、微信号或其他可联系渠道。
- 可选头像。

同时明确不同场景下的可见性：

- 广场和队伍公开详情页展示哪些资料。
- 申请人提交申请后，队长能看到哪些资料。
- 审核通过后，队伍成员之间能看到哪些资料。
- 手机号是否默认隐藏，是否需要用户主动授权展示。

**待确认**

- [ ] 首次登录是否必须完善昵称或头像后才能继续使用？
- [ ] 用户资料是否可随时编辑？
- [ ] 联系方式的可见范围和授权方式是什么？

**【我的回答】**

- 注册时需要填写昵称，不需要头像，头像使用一张默认的，本阶段不实现
- 本阶段不实现用户资料可编辑的功能
- 在一个队伍里，成员之间可以相互看到联系方式；组员提交入组申请时，队长可以看到申请人的联系方式；其他情况都看不到联系方式
- 用户资料按你的设计来

### P0-2：队伍列表和队伍详情缺少决策信息

**当前情况**

需求中写明详情页展示项目简介、队长、队伍名额、当前已组人数和队员要求，但不足以支持用户判断是否申请。

**用户影响**

- 用户不知道队伍具体缺什么角色、还缺几个人。
- 用户无法确认“名额”和“当前人数”是否包含队长。
- 用户无法判断队伍是否已经满员、是否已经停止招募。
- 用户无法判断队伍方向是否与自己匹配。
- 现场组队时，用户可能不知道去哪里找到该队伍。

**建议补充**

队伍卡片和详情页考虑包含：

- 队伍名称。
- 项目一句话介绍。
- 项目完整简介。
- 项目所属赛道或方向。
- 队长信息。
- 招募角色，以及每个角色还缺几人。
- 总名额、当前人数及名额口径。
- 已加入成员及其角色。
- 硬性要求。
- 加分项或偏好项。
- 当前状态。
- 现场位置，例如展位、区域、桌号或集合点。
- 最后更新时间。
- 招募截止时间，如适用。

广场建议至少支持：

- 按状态筛选。
- 按关键词搜索。
- 明确已满员、已结束招募的队伍是否仍展示。
- 明确默认排序规则，例如按更新时间或剩余名额排序。

**待确认**

- [ ] 广场是否只展示“组队中”的队伍？
- [ ] 队伍卡片是否需要展示队长联系方式？
- [ ] 是否需要展示每个角色的独立剩余名额？

**【我的回答】**

- 按你上面的建议，增加筛选、搜索等功能的支持
- 队伍卡片显示队长联系方式。但是要注意，只有队员能看到联系方式，游客是看不到的
- 需要展示每个角色的剩余名额

### P0-3：组队状态与名额规则不明确

**当前情况**

需求要求清晰标识“组队中”和“已完成组队”，但没有定义状态如何变化，也没有定义名额的计算口径。

**用户影响**

- 用户不知道队伍达到人数上限后是否还能申请。
- 队长和成员可能对“当前 3/5 人”是否包含队长产生误解。
- 多个申请同时竞争最后一个名额时，用户可能收到前后矛盾的结果。
- 用户可能同时加入多个队伍，造成队伍人数失真。

**建议明确**

状态定义建议至少覆盖：

- 组队中：仍可接收申请。
- 已满员：人数已达到上限。
- 已结束招募：队长主动停止招募。
- 已解散：队伍不再有效。

也可以将“已满员”和“已结束招募”统一呈现为“已完成组队”，但后台和操作规则仍需区分。

名额规则建议明确：

- 名额是否包含队长。
- 当前人数是否包含队长。
- 达到上限后是否自动变为已完成组队。
- 队长是否可以在未满员时主动结束招募。
- 满员后是否仍可查看申请或恢复招募。
- 一个用户同时最多加入几个队伍。
- 一个用户同时最多提交几个待审核申请。
- 用户已有队伍时，是否还能创建或申请其他队伍。

**待确认**

- [ ] “已完成组队”是由人数满员自动触发，还是由队长手动标记？
- [ ] “名额”和“当前人数”是否统一包含队长？
- [ ] 满员后是否可以重新开放招募？

**【我的回答】**

- 状态和名额规则，按你上面的建议来
- 已完成组队由队长手动触发，有个按钮，队长点一下
- 名额和人数包含队长
- 满员后可以重新开放招募

### P0-4：申请提交后的状态反馈闭环不完整

**当前情况**

需求只描述了“提交申请 → 等待审核 → 审核通过后可以看到自己”，没有定义申请期间和审核结果如何展示。

**用户影响**

- 用户提交后不知道申请是否成功进入待审核状态。
- 用户不知道在哪里查看审核进度。
- 用户可能错过审核通过或被拒绝的结果。
- 用户不知道拒绝理由，无法调整后再申请其他队伍。
- 用户可能重复提交申请。

**建议补充**

申请状态至少包含：

- 待审核。
- 已通过。
- 已拒绝。
- 已撤回。

建议提供：

- 提交成功后的明确反馈页面或提示。
- “我的队伍”或独立申请记录中展示申请状态。
- 审核结果提示、角标或未读提醒。
- 拒绝理由对申请人可见。
- 申请人撤回待审核申请的能力。
- 被拒绝后是否允许再次申请同一队伍。
- 已通过或已加入其他队伍时，其他待审核申请的处理方式。
- 同一用户对同一队伍的重复申请拦截。

**待确认**

- [ ] 拒绝理由是否对申请人展示？
- [ ] 被拒绝后是否允许再次申请？
- [ ] “我的队伍”是否同时展示我申请过但尚未加入的队伍？

**【我的回答】**

- 拒绝理由对申请人展示
- 被拒绝后可以再次申请
- 展示尚未加入的队伍，但是应该显示出不同的标记

### P0-5：文字介绍和申请表单规则不明确

**当前情况**

需求描述为“提交一下文字版的介绍信息，也可以是上传 PDF、图片、视频”。附件上传本阶段不实现，因此需要明确本阶段申请时到底必须填写什么。

**用户影响**

- 用户可能认为不上传附件就无法完成申请。
- 队长可能收到信息量过低、无法判断的申请。
- 前端不知道文字介绍是否必填、是否有长度限制。

**建议补充**

本阶段建议：

- 申请文字介绍设为必填。
- 本阶段不展示附件上传入口，或在页面明确提示附件功能暂未开放。
- 明确文字长度限制和格式要求。
- 建议将申请内容结构化，例如技能、想担任的角色、可投入时间、相关经历、加入动机。
- 提交前允许用户确认内容。
- 提交成功后展示当前状态和后续等待说明。

**待确认**

- [ ] 文字介绍是否必填？
- [ ] 申请是否需要固定字段，还是仅一个自由文本框？
- [ ] 是否允许用户在待审核阶段修改申请内容？

**【我的回答】**

- 文字介绍必填
- 附件上传入口本阶段不展示
- 审核阶段不能修改申请
- 其他的按照你上面的建议来做

### P0-6：队长审核操作规则不完整

**当前情况**

需求明确队长可以同意或拒绝申请，拒绝理由选填，但没有定义审核后的成员数量、冲突和后续操作规则。

**用户影响**

- 最后一个名额被多个申请同时通过时，队伍可能超员。
- 队长可能不知道当前还剩几个名额。
- 被拒绝的用户不知道原因。
- 队长误操作后无法撤回或移除成员。

**建议补充**

队长审核页面建议展示：

- 申请人基本资料和技能信息。
- 申请文字介绍。
- 申请时间。
- 当前队伍人数和剩余名额。
- 申请状态。
- 同意、拒绝操作。
- 拒绝理由输入框。

审核规则建议明确：

- 通过申请时校验剩余名额。
- 名额不足时禁止继续通过，并给出明确提示。
- 通过后是否自动更新队伍人数和状态。
- 拒绝理由是否对申请人可见。
- 队长是否可以撤回审核结果。
- 队长是否可以移除已通过成员。
- 成员被移除后是否需要通知。
- 同一申请是否只能被处理一次。

**待确认**

- [ ] 拒绝理由是否必填、选填，还是申请人不可见？
- [ ] 通过最后一个名额后是否自动关闭招募？
- [ ] 队长是否有权移除已通过成员？

**【我的回答】**

- 拒绝理由为选填
- 通过最后一个名额后不自动关闭招募，也就是设计项目时的人数设置只是一个参考，实际组员数可以超出那个设置的数字，由队长自行决策是否关闭招募
- 队长可以移除已通过的成员

### P0-7：缺少联系方式与现场沟通闭环

**当前情况**

需求没有说明审核通过后，队长和成员如何取得联系、如何找到彼此。

**用户影响**

- 用户审核通过后可能找不到队伍。
- 队长需要到其他平台逐个联系成员。
- “通过审核”并不等于真正完成现场组队。

**建议补充**

至少明确以下一种或多种方式：

- 展示队长或队伍的微信号、手机号。
- 展示微信群二维码或外部沟通群链接。
- 展示现场展位号、桌号、集合区域。
- 提供队伍公告或集合时间。
- 成员通过后可见队伍联系方式。

同时建议明确隐私规则：

- 广场公开页面不展示手机号。
- 申请人联系方式仅队长和相关审核人可见。
- 审核通过后，队伍成员之间可见必要的联系方式。
- 用户是否可以选择是否公开联系方式。

**待确认**

- [ ] 审核通过后由谁先联系谁？
- [ ] 平台内展示联系方式，还是只展示外部群二维码？
- [ ] 联系方式是否需要用户授权后才能展示？

**【我的回答】**

- 只显示手机号这个联系方式就行了，其他的如微信、群二维码等功能，暂时都不做

### P0-8：缺少活动上下文

**当前情况**

产品定位为“黑客松现场组队”，但需求中没有描述当前活动的名称、时间、地点或组队截止时间。

**用户影响**

- 用户不知道当前申请的是哪一场活动的队伍。
- 用户不知道组队何时截止。
- 用户不知道去哪里参加活动或与队伍集合。
- 多场活动使用同一系统时，信息可能混在一起。

**建议补充**

如果当前只服务单场活动，也建议在页面顶部展示：

- 活动名称。
- 组队截止时间。
- 活动开始和结束时间。
- 活动地点。
- 组队人数限制。
- 活动赛道或主题。

如果未来支持多场活动，需要进一步明确队伍和活动之间的归属关系。

**待确认**

- [ ] 当前系统是否只服务一个活动？
- [ ] 组队截止后是否禁止创建队伍和提交申请？
- [ ] 活动结束后是否需要归档或只读展示？

**【我的回答】**

- 活动的信息，暂时都不要加。我们现阶段聚焦于核心的组队功能的实现，其他的功能后续再完善

### P1-1：队伍生命周期和成员管理未定义

**当前情况**

需求定义了创建队伍和审核申请，但没有定义创建后的编辑、退出、移除、转让和解散操作。

**用户影响**

- 队长写错项目信息后无法修改。
- 招募需求变化后无法更新。
- 成员加入后发现不合适，无法退出。
- 队长无法处理人数变化或队伍重组。
- 队长账号不可用时，队伍可能无法继续管理。

**建议补充**

明确以下能力是否在本阶段实现：

- 编辑队伍名称、简介、要求、名额和招募角色。
- 队长提前结束招募。
- 成员主动退出队伍。
- 队长移除成员。
- 队长转让队伍。
- 队长解散队伍。
- 队伍解散或成员退出后的通知和状态变化。

**待确认**

- [ ] 本阶段至少需要支持队长编辑队伍信息吗？
- [ ] 本阶段是否需要成员主动退出？
- [ ] 队伍解散后历史申请如何处理？

---

### P1-2：登录与账号规则不完整

**当前情况**

需求明确了手机号 + 6 位数字验证码登录，开发阶段生成后直接显示验证码，但没有定义验证码有效期、重发规则、账号唯一性和退出后的状态。

**用户影响**

- 用户可能不知道验证码何时过期。
- 用户重复点击发送验证码时，不知道是否需要等待。
- 用户可能用同一手机号产生多个账号。
- 退出后可能残留登录状态或无法确认当前账号。
- 刷新页面后可能丢失登录或申请状态。

**建议补充**

- 明确手机号格式和地区规则。
- 同一个手机号只能对应一个账号。
- 首次登录建议设置昵称。
- 验证码有效期建议为 5 分钟。
- 验证码建议一次性使用。
- 重发验证码建议设置倒计时，例如 60 秒。
- 验证码错误、过期或频繁发送时提供明确提示。
- 开发环境验证码明确标注“仅供开发测试使用”。
- 登录状态在刷新后保持。
- 页面顶部展示当前登录用户。
- 退出后清理会话并回到登录页，便于切换账号。

**待确认**

- [ ] 验证码有效期和重发间隔具体为多少？
- [ ] 首次登录是否强制设置昵称？
- [ ] 退出登录是否需要二次确认？

---

### P1-3：移动端与异常状态未定义

**当前情况**

需求没有说明页面主要面向桌面端还是移动端，也没有定义空状态、错误状态和重复操作时的反馈。

**用户影响**

- 黑客松现场用户很可能使用手机，桌面布局可能无法顺畅操作。
- 用户看到空白页面时不知道是暂无数据还是加载失败。
- 队伍名额刚被抢完时，申请按钮状态可能不一致。
- 重复点击可能造成重复申请或重复创建。

**建议补充**

- 以移动端优先设计，同时兼容桌面端。
- 广场无队伍时展示空状态和“创建队伍”入口。
- “我的队伍”无数据时展示空状态。
- 加载中展示加载状态。
- 网络失败展示可重试的错误提示。
- 满员或结束招募时禁用申请按钮并说明原因。
- 防止重复创建、重复申请和重复审核。
- 关键操作提交后展示成功或失败反馈。

**待确认**

- [ ] 主要使用场景是否为手机浏览器？
- [ ] 是否需要支持微信内置浏览器？
- [ ] 是否需要实时刷新，还是允许用户手动刷新查看申请状态？


---

**【我的回答】**

关于上面的 P1-x 这几条，都大幅的简化，不需要考虑移动端，满足桌面端的使用即可。不必要的规则目前都可以不加。

## 7. 建议的后续补充方式

建议在正式修改 `docs/idea.md` 前，先完成以下三件事：
