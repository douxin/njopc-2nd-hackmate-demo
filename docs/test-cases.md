## 1. 测试目标与范围

### 1.1 测试目标

验证 HackMate 是否形成完整可用的组队闭环：

> 游客浏览 → 注册/登录 → 创建或搜索队伍 → 提交申请 → 队长审核 → 加入队伍 → 查看我的队伍 → 完成组队/重新开放 → 移除成员。

重点验证：

1. 注册、登录、验证码、会话保持和退出登录。
2. 广场浏览、搜索、状态筛选、加载/空/错误状态。
3. 创建队伍、申请加入、队长审核、完成组队、重新开放、移除成员。
4. 手机号等敏感信息的权限可见性。
5. 队伍人数、角色名额、预设名额仅作规划、不自动阻止审核等业务规则。
6. 多个待审核申请、自动关闭申请、重新申请等状态流转。
7. 前后端接口、页面操作和提示文案的一致性。

### 1.2 范围内

- 游客和登录用户的广场、队伍详情浏览。
- 手机号 + 6 位开发验证码注册、登录、退出。
- 创建队伍及必填/选填字段校验。
- 申请加入、审核通过/拒绝、拒绝理由、重新申请。
- 完成组队、重新开放招募、移除成员。
- 我的队伍、待审核申请、拒绝记录、待审核数量。
- 联系方式可见性和关键接口权限。
- 桌面端布局、状态反馈和关键交互。
- 本地 SQLite 初始化、种子数据和接口健壮性。

### 1.3 明确不在本次用例范围

- PDF/图片/视频等附件上传。
- 头像上传、用户资料编辑。
- 移动端适配。
- 活动名称、时间、地点、截止时间。
- 微信、群二维码、站内聊天。
- 队伍编辑、成员主动退出、转让队长、解散队伍。
- 申请人撤回待审核申请。
- 真实短信、验证码有效期、重发冷却、错误次数限制。
- 内容审核、举报、风控。
- 生产部署、高并发、性能压测和多浏览器兼容矩阵。

> 以上能力应通过“不可见/不可调用/不产生入口”的反向用例确认没有被误实现或错误暴露。

## 2. 测试环境与数据

### 2.1 环境

| 项 | 值 |
| --- | --- |
| 操作系统 | macOS，本地开发环境 |
| 后端 | Python 3.11+、FastAPI、SQLite、uv |
| 前端 | React 18、Vite、TypeScript、Tailwind CSS |
| 后端地址 | `http://127.0.0.1:8000` |
| 前端地址 | `http://127.0.0.1:5173` |
| API 文档 | `http://127.0.0.1:8000/docs` |
| 浏览器 | Chrome / Safari / Edge 任一桌面浏览器最新版 |
| 网络 | 本地，无需真实短信服务 |

启动命令：

```bash
# 终端 1
cd backend
uv sync
uv run uvicorn app.main:app --reload --port 8000

# 终端 2
cd frontend
npm install
npm run dev
```

### 2.2 数据隔离与重置

除明确说明外，每个涉及写操作的用例执行前应重置数据库，避免前序用例污染状态：

```bash
# 先停止后端，再执行
rm -f backend/hackmate.db backend/hackmate.db-shm backend/hackmate.db-wal

# 重新启动后端，自动建库并写入演示数据
cd backend
uv run uvicorn app.main:app --reload --port 8000
```

如需空库测试：

```bash
HACKMATE_SEED=0 uv run uvicorn app.main:app --reload --port 8000
```

### 2.5 用例约定

| 标记 | 含义 |
| --- | --- |
| P0 | 核心验收/安全用例，必须通过；失败即阻塞发布 |
| P1 | 重要分支、权限、边界、异常场景，原则上必须通过 |
| P2 | 易用性、提示、视觉和边缘场景，可带缺陷发布但需记录 |
| API | 通过 HTTP 请求直接验证接口行为 |
| UI | 在浏览器中人工验证页面行为和可见性 |
| E2E | 跨多个角色或多个页面的完整业务闭环 |

“期望结果”中提到的接口状态码以当前 FastAPI 返回为准：参数校验错误通常为 `422`，业务冲突通常为 `409`，权限不足通常为 `403`，未登录通常为 `401`，资源不存在通常为 `404`。

## 7. 执行建议

### 7.1 建议执行顺序

1. **环境与冒烟**：NFR-01、NFR-02、NFR-05、SMK-01 至 SMK-04。
2. **认证基础**：AUTH-01 至 AUTH-17，先准备独立的新手机号。
3. **公开浏览**：PLZ-01 至 PLZ-16、DTL-01、DTL-03、DTL-11。
4. **创建队伍**：CT-01 至 CT-15，每轮写操作用新用户或重置数据库。
5. **申请与审核闭环**：APP-01 至 APP-14、REV-01 至 REV-17。
6. **生命周期与成员**：LC-01 至 LC-17。
7. **我的队伍**：MY-01 至 MY-13。
8. **安全专项**：SEC-01 至 SEC-10；必须检查原始 JSON，不能只看页面。
9. **UI/非功能**：UI-01 至 UI-09、NFR-03、NFR-04、NFR-06、NFR-07。

### 7.2 多角色执行方式

- 推荐使用三个独立浏览器会话：队长、申请人、游客/其他登录用户。
- 或使用 API token 分别发起请求，避免浏览器 localStorage 登录态相互覆盖。
- 每个完整 E2E 流程开始前重置数据库，记录操作账号和关键响应。
- 涉及权限的用例必须同时执行“UI 可见性检查”和“直接 API 请求检查”，防止只隐藏按钮而接口仍可越权。

### 7.3 API 测试建议

- 使用 FastAPI `TestClient` + `pytest`，每个测试用独立临时数据库（设置 `HACKMATE_DB`，按需设置 `HACKMATE_SEED`）。
- 用 fixture 创建以下可复用数据：队长、成员、申请人、无队伍用户、待审核申请、已拒绝申请、满员队伍、已完成队伍。
- 自动化优先级：SEC-01 至 SEC-10、AUTH-01 至 AUTH-17、APP-02 至 APP-10、REV-03 至 REV-09、LC-01 至 LC-10、CT-03 至 CT-11。
- UI 自动化建议使用 Playwright，优先覆盖登录、搜索筛选、创建队伍、申请、审核、完成/重开、移除成员七条主路径。

### 7.4 缺陷分级建议

| 等级 | 定义 | 示例 |
| --- | --- | --- |
| S1 阻塞 | 核心流程不可用、数据损坏、越权或敏感信息泄露 | 任意非成员可看到手机号；申请通过后未加入成员；服务端 500 导致无法创建队伍 |
| S2 严重 | 核心业务规则错误但流程可绕行 | 完成组队后仍能申请；拒绝后无法重新申请；待审核重复申请 |
| S3 一般 | 非核心分支、校验、提示或状态展示错误 | 空状态文案错误；筛选排序不符合文档；错误提示不明确 |
| S4 轻微 | 视觉/易用性问题，不影响业务 | 间距、hover、局部截断、非关键文案 |
